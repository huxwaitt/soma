# Wiki overhaul — an agent-kept internal wiki in the vault (administrator 0.2.0)

## 0. What the research says

Three questions were researched (agent-managed wiki frameworks; Obsidian structuring conventions; how memory systems keep facts current). Short version:

**Is there one dominant framework?** Yes, for exactly this idea. Andrej Karpathy's "LLM Wiki" gist (4 Apr 2026, 5k+ stars in days, gist.github.com/karpathy/442a6bf555914893e9891c11519de94f) is what every 2026 implementation cites and reuses: an immutable `raw/` layer the human owns, a `wiki/` layer the model owns entirely, a schema file with the rules, an `index.md` (one line per page, read first), an append-only `log.md`, and three operations — ingest, query, lint. It is an idea file, not software. The hardened derivatives (Hermes Agent's bundled skill, the "v2" gist, the rebuild write-ups) all converge on the same additions:

- Typed frontmatter per page (`type`, `created`, `updated`, `sources`, `contradictions`, `status`, `confidence`).
- Update in place with dated supersession, old claim kept but marked — never silent overwrite, never delete (Graphiti's bi-temporal `valid_at`/`invalid_at` is the cleanest statement of the rule: invalidate only when the new fact is *later*).
- Hard size caps enforced by code that throw an error and force compression (Letta blocks 2,000 chars; Claude Code memory index 200 lines / 25 KB).
- A lint pass with a fixed checklist: orphans, dangling links, index/file mismatch, duplicates, stale pages, oversized pages, contradictions → a human review queue, not auto-resolution.
- Every claim traces to a source; human edits are "pins" that recompilation must not revert.
- Index-first lookup works to ~100–200 pages, then needs per-type indexes and grep.

**Page layout:** Wikipedia's Manual of Style is the most battle-tested contract for lookup: one topic per page, a lead that stands alone and defines the subject, fixed section order, aliases/disambiguation first, "summary style" (a section that grows gets its own page and a one-line pointer). Matuschak's evergreen rule — one concept = one page, declarative title — is the dedupe unit. Gwern's `status` / `confidence` / "last meaningful modification" are the accuracy metadata.

**What fails in practice (HN threads on the gist, the STALE and MemFail benchmarks):** confidently stale pages nobody can tell are stale; bloat ("everyone is writing, nobody is reading"); duplicate entities past ~150 pages because the model forgets a page exists; verbose rewrites that drift from terse to padded; contradictions accumulating faster than they are resolved; parallel ingest forking the wiki; recompilation reverting human edits; index out of sync with files. The one thing practitioners agree works: "draft freely, promote on approval" — human gates on anything the code cannot decide.

**Decision:** adopt the Karpathy three-layer pattern, with Wikipedia's page contract, Graphiti's supersession rule, Claude-Code-style caps, and Mem0's four write operations (ADD / UPDATE / SUPERSEDE / NOOP) executed by code. Everything the research lists as a failure mode gets a named countermeasure below (§9).

## 1. What we already have, mapped onto the pattern

| Karpathy layer | In the vault today | Verdict |
|---|---|---|
| `raw/` — immutable sources | `Emails/`, `Meetings/` (body never edited; `## Update` only), `Daily/`, `Weekly/`, `Attachments/` | Already right. Stays as is. These are the *records*. |
| `wiki/` — model-owned pages | `People/` (half-way: identity + aliases + append-only lists) | The only wiki-like thing. Becomes one page type of five. |
| schema file | `skills/administrator/references/vault.md` + `notes.py` | Extend, same pattern: prose reference + Python enforcement. |
| `index.md` | none (Bases views are per-type tables, human-facing) | Add, generated by code from frontmatter — never hand-written, so it cannot drift. |
| `log.md` | none | Add, append-only, code-written. |
| ingest / query / lint | `save` and `notes` write records only; `prep`/`find` read records; no lint | Ingest becomes the last step of `save`, `notes`, `weekly`. Query = `vault_wiki_match`. Lint = new `/administrator:lint`, also run by `weekly`. |

The overhaul therefore adds a **`Wiki/` folder next to the records**, does not touch how records are written, and moves `People/` under it.

## 2. Folder layout

```
<vault>/Administrator/
  Emails/  Meetings/  Daily/  Weekly/  Attachments/   ← records, unchanged
  Follow-ups.md  Preferences.md  Rules.md              ← unchanged
  Wiki/
    Index.md          ← generated: one line per page, grouped by type
    Log.md            ← generated: append-only, `- [ISO] op | page | source`
    Review.md         ← generated: open questions for the user (contradictions, suspected duplicates, stale pages)
    Wiki.md           ← the schema, copied from the plugin by vault_init (never edited by the plugin afterwards; user may annotate)
    People/<Display Name>.md
    Orgs/<slug>.md
    Topics/<slug>.md
    Howto/<slug>.md
  _views/ Wiki.base  (+ existing .base files)
```

Rules:

- Flat: at most one folder level under `Wiki/`. No sub-folders per topic. Hierarchy is expressed by links and the index, not paths (LYT/Matuschak; deep folders are what Johnny.Decimal users regret).
- Filenames never change after creation. A page that needs a better name gets the new name as `title` + `aliases`; the file stays. Reason: Obsidian only rewrites `[[links]]` when the rename happens inside Obsidian; an external rename silently orphans every link.
- Filenames are slugs: `Topics/q3-budget.md`, `Orgs/example-gmbh.md`, `Howto/submit-expense-claim.md`. `People/` keeps `<Display Name>.md` (already in use, already linked from every email note). Slug = lowercase, ASCII, `-` separators, ≤ 40 chars, no dates, no stop-word stripping (keep it predictable).
- `Wiki/People/` replaces `Administrator/People/`. Migration (§10) moves the files and rewrites `[[People/…]]` → `[[Wiki/People/…]]` in all records in one pass, by code, with a dry-run report first.

## 3. Page types — the MECE axis

Five types, chosen so that **every fact has exactly one home**, decided by what the fact is *about*, never by where it came from:

| Type | One page per… | Holds | Does not hold |
|---|---|---|---|
| `person` | real person (SMTP identity; aliases absorb other addresses/spellings) | role, organisation link, what they are responsible for, how they work with the user, current asks in both directions | thread content (→ record), project state (→ topic) |
| `org` | company / department / team that appears as a counterparty | what they are to the user, contacts (links), contract/commercial facts, conventions | people's personal facts |
| `topic` | a subject with a timeline and an outcome — project, deal, recurring decision area, an ongoing issue | current state (lead), dated facts, who is involved, what is open, key records | the running log of every mail (→ records + History) |
| `howto` | a procedure the user performs (Diátaxis how-to) | steps, where, who approves, gotchas, last time it was done | explanations of why (→ topic) |
| `me` | exactly one page: `Wiki/Me.md` (optional; `Preferences.md` stays the settings file) | stable facts about the user's role, team, recurring duties, preferences the model should know when drafting | anything that changes weekly |

Decision table the model applies when placing a fact ("where does this go?"), in order:

1. Is it a step-by-step way of doing something? → `howto`.
2. Is it about one person's role, responsibility, preference, or their relationship to the user? → `person`.
3. Is it about a company/team as a whole (contract, address, policy, who-does-what there)? → `org`.
4. Does it have a timeline and an end state (deadline, decision, deliverable, problem being resolved)? → `topic`.
5. Otherwise it is not wiki material. It stays in the record (email/meeting note) and is reachable through `find`.

Two facts about the same thing never live on two pages: the page for the *subject* holds the fact, the other pages *link*. A topic page lists people by link with a three-word role; the person page lists topics by link with a three-word role. Both lists are generated from the same link graph by code (§6, `related` section), so they cannot disagree.

**When does a topic page come into existence?** Not on first sight. A `topic` is created only when the same subject appears in **≥ 2 records on ≥ 2 different days**, or the user names it. Before that the records are enough. This one rule is the main bloat control: one-off mails never become pages. Candidate subjects are tracked in code (`Wiki/_cache/candidates.json`: normalised conversation subject → record paths/dates), and `vault_wiki_ingest` proposes page creation when a candidate crosses the threshold.

### 4.1 Frontmatter keys

| Key | Type (Obsidian property) | Set by | Meaning |
|---|---|---|---|
| `type` | text | code | `person` / `org` / `topic` / `howto` / `me` |
| `title` | text | model at create; changeable via `retitle` op (file name does not change) | Declarative, noun phrase, ≤ 6 words, no dates |
| `aliases` | list | merged by code (never removed by code) | Other names, spellings, addresses; what `vault_wiki_match` searches. Obsidian uses them for `[[alias]]` resolution and unlinked mentions. |
| `summary` | text | model (`summary` op), ≤ 160 chars | The one line that goes into `Index.md`. The only thing a lookup reads before deciding to open the page. |
| `status` | text | model op / lint | `active`, `dormant` (no record in 60 days), `closed` (outcome reached), `draft` (created by code, no lead yet) |
| `owner` / `org` | text (quoted wikilink) | model | Optional |
| `created` | date | code | |
| `updated` | datetime | **code, on every write** | Last time anything below the frontmatter changed. Never set by the model. |
| `verified` | date | code | Date of the newest *source* that confirmed or added a fact (not the write date). "Accurate as of" beats "last updated". |
| `sources` | number | code | Count of distinct record links in Facts + Records. |
| `open_items` | number | code | Unchecked boxes in `## Open`. |
| `flags` | list | code / lint | `contradiction`, `possible-duplicate`, `stale`, `oversized`, `orphan`. Empty list = clean. |
| `created_by` | text | caller | |

`created`, `updated`, `verified`, `sources`, `open_items`, `flags` are **code-owned**: `vault_wiki_*` refuses a frontmatter that tries to set them.

### 4.2 Sections — fixed order, fixed meaning

| Section | Written by | Rule |
|---|---|---|
| Lead (text between `# Title` and the first `##`) | model (`lead` op), ≤ 80 words, 2–4 sentences | Stands alone: what the thing is and its current state. Rewritten in place — this is the one place the model replaces text. No links required (they live below). |
| `## Facts` | code, from model ops | One bullet = one claim, ≤ 25 words, present tense, no hedging words. Each ends with the hidden comment `<!-- f:<id> since:<date> src:<record id> -->`. `since` = date the claim became true per the source (Graphiti `valid_at`), `src` = `internet_message_id` / `occurrence_key` / `user`. Only **current** facts. |
| `## People` (`## Contacts` on org pages, `## Topics` on person pages) | code | Link + ≤ 4-word role, sorted by role then name. Regenerated from the link graph + `role` ops. |
| `## Open` | code | Checkbox lines, each linking the record it came from; mirrors `Follow-ups.md` rows and record action items that reference this page. `- [x]` lines move to History on the next write. |
| `## Records` | code | `- <date> — [[record]] — <summary line from the record's frontmatter/Summary>`, newest first, capped at 15; older ones are reachable via `vault_list`/`find`. |
| `## Related` | code | Links to other wiki pages, derived from (a) `related` ops, (b) any wiki page linked from this page's Facts, (c) back-links. Symmetric by construction. |
| `## History` | code, append-only | `- <date> — <op> <detail> ([[record]])`. Superseded facts land here with old → new text. Capped at 40 lines; older lines are rolled into `Wiki/_history/<page>.md` by lint, with one pointer line left. |
| `## Notes` | **user only** | The pin. Code never reads or writes below this heading. If a user fact in Notes contradicts a Fact, lint reports it; the user's text wins by default. |

Sections are recognised by exact heading text; a page missing a section gets it added in order on the next write. A page with an unknown `## Heading` before `## Notes` fails lint (`unknown-section`) rather than being "fixed".

### 4.3 Per-type variations

- `person`: sections Facts / Topics / Open / Records / Related / History / Notes. Extra frontmatter: `email`, `org`, `last_contact` (code). Lead = role, organisation, how they relate to the user. The current `Voice with this person:` block, if present, is preserved under `## Notes` by migration.
- `org`: Facts / Contacts / Topics / Records / Related / History / Notes. Extra: `domains` (list, used by `vault_wiki_match` on sender domain).
- `topic`: as shown. Extra: `owner`, `org`, `due` (date, optional, set by model op; lint flags `due` in the past on an `active` page).
- `howto`: Lead / `## Steps` (numbered, model-written via `steps` op — the one multi-line free-text section; replaced whole) / Facts / Records / Related / History / Notes. Extra: `last_done` (date, code: newest record date).
- `me`: Lead / Facts / Related / History / Notes only.

### 4.4 Size caps (enforced, not advisory)

| Type | Max lines | Max chars (≈ tokens) |
|---|---|---|
| person, org, howto | 80 | 4,000 (~1k) |
| topic | 120 | 6,000 (~1.5k) |
| Facts section, any type | 25 bullets | — |
| Lead | 80 words | — |
| `Index.md` | 200 lines | 25,000 |

A write that would exceed a cap is **refused** with the measured sizes and the suggestion: supersede/merge facts, move detail to a new page (Wikipedia summary style: leave a one-line pointer fact), or close the page. The model must then send a smaller op set. `Index.md` over 200 lines switches itself to one `Index.md` per type folder (`Wiki/Topics/Index.md` …) plus a 6-line root index pointing at them.

## 5. Facts, identity, supersession — the accuracy machinery

### 5.1 Fact ids and the four operations

A fact id is 4 chars from base32 of a random value, unique within the page. The model never invents ids; it uses the ones `vault_wiki_read` returned. Operations (Mem0's set, with delete replaced by supersede):

| op | fields | what code does |
|---|---|---|
| `add` | `text`, `since`, `src` | New bullet, new id. Refused if `text` is identical (case/whitespace-insensitive) to an existing fact → treated as `confirm`. |
| `update` | `id`, `text`, `src` | Same claim, more or better wording/detail; id kept, `since` kept, `src` extended (a fact can have several sources — `src:` becomes a comma list, capped at 3, newest first). History line: `updated f:<id>`. |
| `supersede` | `id`, `text`, `since`, `src` | The claim changed (date moved, owner changed, decision reversed). Allowed only if new `since` ≥ old `since`; otherwise refused with `older-than-current` and the pair is written to `Review.md` instead. Old bullet moves to History as `superseded "<old>" → "<new>"`; new bullet gets a new id. |
| `confirm` | `id`, `src` | Source repeats a known fact; `src` extended, `verified` bumped. No text change. This is what keeps `verified` honest without rewriting. |
| `retire` | `id`, `src`, `reason` | The fact is no longer true and has no replacement (project cancelled). Moves to History as `retired "<old>" — <reason>`. |

Plus page-level ops: `lead`, `summary`, `status`, `title`, `alias` (add only), `related` (add link), `role` (`page`, `role`), `open` (`text`, `src`), `steps` (howto), `due`, `owner`, `org`. Every op carries `src`. Ops without a source are refused except `lead`, `summary`, `title`, `related`, `role`.

`noop` is implicit: the model sends an empty op list; code still appends `## Records` line and History `seen` line if the record is new to the page.

### 5.2 The two supersession rules (from Graphiti)

1. **Later wins, only if later.** `supersede` requires the new fact's `since` (the date the source says it became true — usually the record's received/start date) to be ≥ the current fact's `since`. A freshly ingested *older* mail cannot overwrite a newer fact. That is the whole defence against "stale overrides fresh" when the user saves an old thread.
2. **Nothing is deleted.** Every superseded/retired line is in History with both texts, the date, and the record link. `Log.md` has the same line. Reverting = a new `supersede` the other way.

### 5.3 Contradiction handling

Code cannot detect a semantic contradiction; the model can, but it should not resolve it alone. Protocol:

- At ingest the model reads current Facts (§7.1). If the new source contradicts a fact and the new source is later → `supersede` (normal path, logged).
- If the new source contradicts a fact but is **older or same-day**, or the model is unsure which is right → op `contest` (`id`, `text`, `src`). Code sets `flags: [contradiction]`, appends to `Review.md`: `- [ ] <page> — f:<id> "<current>" vs "<new>" ([[record A]] / [[record B]])`, and leaves Facts unchanged.
- `Review.md` is a checklist the user works through in Obsidian or in chat ("resolve review"). Ticking a box does nothing by itself; the resolution is a normal op from the user's answer. Lint reports the count of open review items; `weekly` lists them.

### 5.4 User pins

Anything under `## Notes` and any fact with `src:user` (typed by the user in chat and written via ops) outranks model facts: code refuses `supersede`/`retire` on a `src:user` fact from a non-user source and routes it to Review instead.

## 6. Index, log, and views — lookup without reading the vault

### 6.1 `Wiki/Index.md` (generated)

```markdown
---
type: wiki-index
updated: 2026-08-22T09:40:00+02:00
pages: 37
---
# Wiki index

## Topics (12)
- [[Wiki/Topics/q3-budget|Q3 budget]] · active · 2026-08-22 — Final Q3 numbers due to Jane by 2026-08-29; forecast closes 2026-09-02.
- …

## People (18)
- [[Wiki/People/Jane Doe]] · Example GmbH · 2026-08-22 — Finance lead; owns the quarterly forecast; prefers short mails.

## Orgs (5) … ## Howto (2) … ## Me
```

One line per page: link with title, status (or org for people), `verified` date, summary. ~25 tokens per line. Regenerated in full after every wiki write from frontmatter alone — it *cannot* drift from the files. Sorted: `active` before `dormant` before `closed`; within that, `verified` newest first, so the first screen is what matters now. `closed` pages beyond 20 collapse to a count and live only in the per-type index.

### 6.2 `Wiki/Log.md` (generated, append-only)

`- [2026-08-22T09:40:00+02:00] ingest | Wiki/Topics/q3-budget | [[Emails/2026-08-22 Budget Q3]] | add 2, supersede 1`
One line per page per ingest, one per lint run, one per migration. Rotated to `Wiki/_history/Log-YYYY.md` at 500 lines. Grep-able; `vault_wiki_log(since, page)` returns slices so the model never reads it whole.

### 6.3 `Wiki/Review.md` (generated)

Checklist of things code could not decide: contradictions (§5.3), suspected duplicate pages (§8), pages flagged stale, proposed topic creations awaiting a yes (when the user asked to be consulted), refused supersedes. Each line links the page and the records. Resolved lines move to a `## Done` section with the date.

### 6.4 Obsidian views

`_views/Wiki.base`: tables over `Wiki/**` — "Active topics by verified", "Stale (flags contains stale)", "Review queue" (pages with non-empty flags), "People by org". Bases read frontmatter only, which is exactly what the code maintains, so the views are never stale. `Index.md` doubles as the human home page; `obsidian://open` links in chat point to pages.

## 7. Tools (the `administrator-vault` server)

New module `src/administrator_vault/wiki.py` (page model, ops, caps, index, log) and `wiki_lint.py`. Nine tools:

| Tool | In | Out | Tokens |
|---|---|---|---|
| `vault_wiki_match(text, people=[], domains=[], limit=8)` | free text (subject + first 300 chars), attendee/sender addresses, sender domains | index lines of pages whose title/aliases/email/domains match (exact alias hit > word overlap ≥ 2 words > domain), plus topic *candidates* over threshold | ≤ 300 |
| `vault_wiki_read(path, sections=["lead","facts"], max_chars)` | page | frontmatter + requested sections; Facts as JSON `[{id, text, since, src}]` | 300–800 |
| `vault_wiki_ingest(record_path, pages=[{path|new:{type,title}, ops:[…]}], created_by)` | the record and per-page op lists | per page: applied / refused ops with reasons, new ids, cap report; writes Records + History + Log + Index; records the candidate count | ≤ 200 |
| `vault_wiki_create(type, title, aliases, lead, summary, facts=[…], src, created_by)` | | path; refused if an existing page matches title/alias (returns the match — "you meant this page?") | |
| `vault_wiki_apply(path, ops, created_by)` | ops without a record (user said something in chat; `src:user`) | as ingest | |
| `vault_wiki_lint(fix=false)` | | report (§8); with `fix=true` applies the safe fixes | ≤ 600 |
| `vault_wiki_log(since, page, limit)` | | log lines | |
| `vault_wiki_review(action="list"|"resolve", item, resolution_ops)` | | | |
| `vault_wiki_migrate(dry_run=true)` | | the People move + link rewrite plan / result (§10) | |

Rules inside the server:

- **Serialised writes.** One `threading.Lock` around every wiki write and a `Wiki/.lock` file with pid + timestamp for cross-process safety (a second Claude session). A held lock older than 60 s is taken over. Parallel ingest is what forks wikis; we do not allow it.
- **Exact-match edits only.** Facts are located by id, sections by exact heading; the lead is replaced between `# Title` and the first `##`. No fuzzy replacement anywhere.
- **Atomic writes**: write to `<file>.tmp`, `os.replace`. Obsidian sees one change.
- **Record linkage is two-way by code**: ingest appends `wiki: ["[[Wiki/Topics/q3-budget]]"]` to the record's frontmatter (new replaceable list key on email/meeting notes) so `prep`, `find` and the Bases views can show which pages a record feeds.

## 8. Lint — the fixed checklist

`vault_wiki_lint()` runs deterministic checks first; only the last two need the model and come back as questions, not fixes.

| # | Check | Fix mode |
|---|---|---|
| 1 | Index ↔ files: page without index line / line without page | auto (regenerate) |
| 2 | Dangling `[[links]]` anywhere under `Wiki/` (target missing) | report; `fix=true` turns the link into plain text *only* inside code-owned sections |
| 3 | Orphans: page with no inbound link from any wiki page or record | flag `orphan`; report |
| 4 | Frontmatter schema: missing/extra/mistyped keys, code-owned keys edited by hand | auto (recompute code-owned; report the rest) |
| 5 | Section order / unknown sections / duplicate headings | report (`unknown-section`); order auto-fixed |
| 6 | Oversized page (caps §4.4) | flag `oversized`; report with the three remedies |
| 7 | Stale: `status: active` and `verified` older than 60 days (topic/howto) or 120 days (person/org) | flag `stale`; `fix=true` sets `status: dormant` for topics only, logs it |
| 8 | `due` in the past on an active topic | report |
| 9 | Open items whose record action item is checked `- [x]` | auto-move to History |
| 10 | Duplicate entities: two pages sharing an alias, an email address, or a domain; titles equal after normalisation (case, punctuation, stop words `the/a/of`) | flag `possible-duplicate` on both; Review line "merge A into B?" (merge = §8.1, only on a yes) |
| 11 | Records never ingested: email/meeting notes with no `wiki:` key, newer than the wiki's last ingest | report count + list; the `weekly` command offers to ingest them |
| 12 | Topic candidates over threshold without a page | report (proposal) |
| 13 | `History` over 40 lines / `Log.md` over 500 | auto-rotate |
| 14 | Contradictions (model): for pages touched since the last lint, the model reads Facts and reports pairs that cannot both be true | Review line only |
| 15 | Facts with `since` older than 180 days never confirmed (`src` has one source) on active pages | report as "unconfirmed", grouped, ≤ 20 per run |

Output: a JSON report + a written `Wiki/_cache/lint-<date>.json`, and the chat summary: counts per check, the Review lines added, the pages flagged. `/administrator:lint` runs it; `weekly` runs it with `fix=true` for the auto-fixable checks and lists the rest under `## Wiki`.

### 8.1 Merge (only ever on a yes)

`vault_wiki_merge(keep, drop)`: Facts from `drop` are appended to `keep` as `add` ops with their original `since`/`src` (duplicate text → `confirm`); aliases, Records, Related merged; `drop`'s file becomes a 3-line redirect page (`type: redirect`, `redirect: "[[keep]]"`, lead "Merged into [[keep]] on <date>") so no link breaks; index skips redirects; History on `keep` records the merge. Graphiti's rule applies: merge only when the model says "same real-world referent", never on name similarity alone — similarity only produces the Review question.

## 9. Failure modes → countermeasure

| Reported failure | Here |
|---|---|
| Confidently stale pages | `verified` = newest source date, not write date; stale flag at 60/120 days; `status: dormant` by lint; index sorted by `verified` |
| Stale overrides fresh | `supersede` only if `since` is later; otherwise Review |
| Silent overwrite / lost history | no delete op; History + Log with both texts |
| Bloat | topic threshold (2 records, 2 days); size caps refuse writes; Records capped at 15; `confirm` instead of re-adding; one fact = one bullet ≤ 25 words |
| Verbose drift | lead ≤ 80 words and Facts ≤ 25 words enforced by code; the model replaces the lead only, never the page |
| Duplicate entities | `vault_wiki_create` refuses on alias/title/email match; lint 10; merge on yes with redirect |
| Index drift | index is generated from frontmatter after every write; never hand-edited |
| Forked wiki from parallel writes | write lock; ops are applied one page at a time |
| Human edits reverted | `## Notes` untouched; `src:user` facts protected; code-owned keys are the only frontmatter it rewrites |
| Contradictions piling up | Review.md with a count in `weekly`; contradictions never silently resolved |
| Navigation collapse at scale | per-type indexes over 200 lines; `vault_wiki_match` instead of reading the index; grep over aliases in code |
| "Everyone writes, nobody reads" | every workflow that *reads* (`prep`, `find`, `draft`, `daily`) calls `vault_wiki_match` first and shows the lead; pages that are never matched show up in lint 15 (unconfirmed) and go dormant |

## 10. Migration from 0.1.0 vaults

`vault_wiki_migrate(dry_run=true)` prints the plan; `false` does it, under the lock, with a backup copy `Administrator/_backup/<ISO>/People/`:

1. Create `Wiki/`, `Wiki.md` (schema copy), empty `Index.md`, `Log.md`, `Review.md`.
2. Move `People/*.md` → `Wiki/People/`. For each: keep `name`, `email`, `aliases`, `last_contact`, `company` → `org` text (no org page is created — lint 12-style proposal later); add code-owned keys; lead = `"<name> (<email>) — <company>."` with `status: draft` so the model fills the lead on first ingest; `## Emails` / `## Meetings` / `## Update` lines become `## Records` (newest 15) and `## History` (`- <date> — migrated`); any `Voice with this person:` block and anything after the last generated list → `## Notes`.
3. Rewrite links in all records, `Follow-ups.md`, daily and weekly notes: `[[People/` → `[[Wiki/People/`, also in frontmatter (`from_link`, `organizer_link`, `attendee_links`). Regex on `\[\[People/`, counted and reported.
4. Update `.base` views' folder filters.
5. Generate the index; one Log line `migrate | <n> people, <m> links`.
6. Old `People/` folder removed only when empty (it will be, unless the user put other files there — then reported and left).

The plugin side: `person_filename` / `folder_of("person")` in `notes.py` move to `Wiki/People`; `vault_save_email` writes the person page through the wiki module (`confirm`/`add` for role facts are the model's job in the ingest step; `save_email` itself only creates the `draft` person page and the Records line).

Ingest prompt shape (in `skills/wiki/SKILL.md`, < 100 lines): "For each matched page, compare the record with the Facts list. Emit ops only for what the record adds, changes, or confirms. One bullet per claim, ≤ 25 words, present tense, with `since` from the record date unless the text states another date. Do not restate the record's summary; do not add facts the record does not contain. A fact you cannot place in §3's table stays out." Worked examples in `references/examples.md` (one save, one notes, one contradiction), the placement table and page contract in `references/wiki.md` — which `vault_init` also copies into the vault as `Wiki/Wiki.md` so the human and the model read the same schema (Karpathy: the schema co-evolves; user annotations in `Wiki.md` are read by `wiki` on demand, never by every command).

## 12. Token budget, concretely

| Item | Size |
|---|---|
| Index line | ~25 tokens; 200 pages = 5k — never loaded whole; `vault_wiki_match` returns ≤ 8 lines (~200) |
| `vault_wiki_read(lead+facts)` | 300–800 per page; ingest reads ≤ 3 pages |
| Op list for one record | 100–400 |
| `wiki` SKILL.md | ≤ 100 lines, loaded only by `wiki`, `lint`, and the ingest step (commands say "load skills/wiki"); `save`/`notes` load it only after the record is written |
| Lint report | ≤ 600 |

So a `save` with ingest lands at ~4–6k total instead of ~2–3k today; `notes` ~7–9k. In exchange `prep`/`find` stop re-reading old records. Measured, as before, via `tokens_used` in the daily note; the ingest step is skippable with "save without wiki".

## 13. Build order

Three agents, one batch, `model: 'fable'`, then reviewer + verifier as in batch 3. No further features.

1. **Server — wiki core** (`wiki.py`): page model (parse/format with the exact section contract), ids, ops + refusal rules, caps, supersession rules, record two-way link, index/log/review generation, lock, atomic write; `vault_wiki_match/read/ingest/create/apply/log/review`. Tests with a temp vault: every op, every refusal (`older-than-current`, cap, duplicate title, user-pin), index regeneration, lock takeover, the `|` / `<!--` escaping inherited from store.
2. **Server — lint + migrate** (`wiki_lint.py`, `wiki_migrate.py`): the 15 checks (14 returns "pages to ask the model about"), merge with redirect, migration with dry run and backup, `.base` view. Tests: a fixture 0.1.0 vault with 3 people, 5 emails, 2 meetings → migrate → every link resolves, index has 3 lines, old folder gone; lint on a seeded vault hits every check once.
3. **Plugin**: `skills/wiki/` (SKILL.md, `references/wiki.md` = the schema above in user words, `references/examples.md`), `commands/wiki.md`, `commands/lint.md`, ingest steps added to `save` / `notes` / `weekly` skills, `prep`/`find`/`draft` read steps, `vault.md` updated (People path, `wiki:` key), `setup` migration offer, version 0.2.0, banned-word check, every SKILL.md still < 120 lines.
4. **Reviewer**: contract in `references/wiki.md` vs `wiki.py` line by line (headings, caps, key names, op names, refusal strings); **verifier** runs the tests and a scripted end-to-end on a temp vault: migrate → save-ingest → notes-ingest with a superseding decision → older mail refused → lint → merge on yes.

After that: the v0.6 real run, with the wiki included — the week's question for this part is simply "after five days, does `Wiki/Index.md` read like what I actually have going on, and did I ever catch it being wrong?"

## 14. Decisions taken here, so they are not re-argued

- No vector search, no embeddings, no plugin dependency (Dataview etc.). Grep over aliases + index is enough to ~200 pages, which is years of a one-person vault.
- No numeric confidence (false precision, per the v2 gist's critics). `verified` date + source count + `flags` carry the same information honestly.
- No "concept"/"synthesis" page types from Karpathy's research use case; for an assistant, the subjects are people, organisations, topics with outcomes, and procedures. Answers to questions are not filed as pages (the user did not ask for an encyclopedia; `find` answers from records).
- No automatic page creation from a single mail. Threshold or explicit ask.
- No automatic merge, no automatic contradiction resolution, no automatic deletion. Those three are the human gate.
- The model rewrites exactly two things freely: the lead and (howto) the steps. Everything else is an op on a keyed line, applied by code.
